### Documentation / policy — v1.4 scope and persistence are now stated, not inferred (card Y9)

No behaviour changed. Three founder decisions that were previously only implicit in the code are now
written where a reader will hit them — ADR-006 §Consequences, the module docstrings of
`percept/sourceprofile.py` and `percept/episodes.py`, and a new client-facing reference page
`docs/reference/v1-4-scope-and-persistence.md` (linked from the docs index and the integration
guide):

- **Scope is narrow for contract v1.4** — screen documents with stable content keys, and
  conversational claim slots with explicit mutation semantics. Biometric re-identification, growth
  prediction and robotics control are **explicitly excluded** (scope, not backlog). The resolver seam
  (`SourceProfile.identity_strategy`, open registry) stays open so a future scheme can be registered,
  but v1.4 does not generalise ahead of evidence.
- **Persistence is session-only** — episodes are NOT persisted across restart (`Percept.snapshot()`
  does not carry the `episodes` map, so `restore()` cannot rehydrate it). This blocks any 24/7
  viability claim until a later phase. `scope='durable'` on a subject reference describes
  **identifier stability** (`PO-4471` means the same thing next week) and must never be read as
  restart-safety of episode state — that caveat now sits beside the field, not in a distant doc.
- **Delivery is provisional incident + superseding revision**, not a wide settle window: emit on the
  rising edge immediately and supersede when a correction lands; any delay is concern-specific and
  bounded by a declared latency SLO.

New drift guard `tests/test_y9_scope_and_persistence_policy.py` pins each statement in place and
asserts the persistence claim against the code (`snapshot()`/`restore()`), so it cannot silently
become a lie.
